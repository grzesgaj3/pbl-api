# API reference

Base URL: `http://<host>:8000/api/v1`

All requests and responses are JSON. Every endpoint except the health checks
requires an `X-API-Key` header.

## Authentication

| Credential | How to obtain | What it can do |
|------------|---------------|----------------|
| **Bridge key** | `python -m app.scripts.create_bridge <bridge_id>` | Post measurements; read own measurements and commands; acknowledge/reject own commands. |
| **Admin key** | `ADMIN_API_KEY` in `.env` | Create cleaning commands; read measurements and commands from every bridge; list bridges and sensors. |

The `bridge_id` of a measurement or command is always derived from the bridge
key — it is never taken from the request body, so a bridge cannot write or read
data belonging to another bridge.

```bash
curl -s http://localhost:8000/api/v1/measurements -H "X-API-Key: <key>"
```

Missing key → `401`, unknown or deactivated key → `403`.

## Errors

Every failing request returns the same envelope:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed.",
    "details": [
      {"loc": ["body", "value_mm"], "msg": "Input should be greater than or equal to 0", "type": "greater_than_equal"}
    ]
  }
}
```

| Status | `code` | Meaning |
|--------|--------|---------|
| 401 | `unauthorized` | Missing `X-API-Key`. |
| 403 | `forbidden` | Key is invalid, inactive, or lacks the required role. |
| 404 | `not_found` | Resource missing, or not visible to this caller. |
| 409 | `conflict` | Command already answered, or a measurement with the same `sensor_id` and `sent_at` belongs to another bridge. |
| 422 | `validation_error` | Request body or query parameters are invalid. |
| 503 | `service_unavailable` | `/health/ready` could not reach the database. |

## Pagination

List endpoints accept `limit` (1–1000, default 100) and `offset` (default 0)
and return:

```json
{
  "items": [ /* ... */ ],
  "limit": 100,
  "offset": 0,
  "count": 1,
  "has_more": false
}
```

`has_more` tells the client whether at least one more row exists.

## Health

### `GET /health`

Liveness probe. Does not touch the database.

```json
{"status": "ok", "version": "1.0.0"}
```

### `GET /health/ready`

Readiness probe. Executes `SELECT 1`; returns `503` if the database is
unreachable.

## Measurements

A measurement is one rainfall reading.
`sent_at` is the device transmit time sent as **epoch seconds (UTC)**;
`recorded_at` is generated by the database when the row is inserted.

| Field | Type | Notes |
|-------|------|-------|
| `id` | integer | Primary key. |
| `bridge_id` | string | Taken from the API key. |
| `sensor_id` | string | Measuring station, e.g. `sensor1`. |
| `value_mm` | number | Rainfall in millimetres (`DECIMAL(6,2)`). |
| `sent_at` | string | ISO 8601 UTC, `Z` suffix. |
| `recorded_at` | string | ISO 8601 UTC, database clock. |

### `POST /measurements` — bridge

Store one reading. Idempotent on `(sensor_id, sent_at)`:

- new row → **`201 Created`**
- already stored by the same bridge → **`200 OK`** with the existing row (no duplicate)
- already stored by a *different* bridge → **`409 Conflict`** (another bridge's
  row is never returned)

```bash
curl -s -X POST http://localhost:8000/api/v1/measurements \
  -H "X-API-Key: <bridge key>" \
  -H "Content-Type: application/json" \
  -d '{"sensor_id": "sensor1", "value_mm": 3.4, "sent_at": 1729260000}'
```

```json
{
  "id": 1,
  "bridge_id": "mostek1",
  "sensor_id": "sensor1",
  "value_mm": 3.4,
  "sent_at": "2024-10-18T14:00:00Z",
  "recorded_at": "2026-10-18T12:44:50Z"
}
```

Validation: `sensor_id` 1–64 characters (trimmed, non-blank), `value_mm`
`0 … 9999.99` with at most 2 decimals, `sent_at` a non-negative integer.

### `GET /measurements` — bridge or admin

Query parameters: `sensor_id`, `sent_from`, `sent_to` (epoch seconds,
inclusive), `limit`, `offset`. Admins may also pass `bridge_id`.

A bridge only ever sees its own rows.

```bash
curl -s "http://localhost:8000/api/v1/measurements?sensor_id=sensor1&limit=10" \
  -H "X-API-Key: <admin key>"
```

Results are ordered by `sent_at` descending, then `id` descending.

### `GET /measurements/{id}` — bridge or admin

Returns one measurement. A bridge requesting another bridge's row gets `404`.

## Stations

Read-only listings of the registered **bridges** (receiving stations) and
**sensors** (measuring stations). Both endpoints are **admin only** and never
return a bridge's API-key hash. They give the admin panel the bridges and
sensors it needs to pick before posting a cleaning command.

### `GET /bridges` — admin

Query parameters: `is_active` (`true`/`false`), `q` (substring of `bridge_id`),
`limit`, `offset`. Ordered by `bridge_id`.

| Field | Type | Notes |
|-------|------|-------|
| `bridge_id` | string | Station identifier. |
| `is_active` | boolean | Whether the bridge may authenticate. |
| `created_at` | string | ISO 8601 UTC, database clock. |
| `last_seen_at` | string \| null | Last authenticated request (refreshed at most hourly). |

```bash
curl -s "http://localhost:8000/api/v1/bridges?is_active=true" \
  -H "X-API-Key: <admin key>"
```

```json
{
  "items": [
    {
      "bridge_id": "mostek1",
      "is_active": true,
      "created_at": "2026-10-18T12:44:50Z",
      "last_seen_at": "2026-10-18T13:05:00Z"
    }
  ],
  "limit": 100,
  "offset": 0,
  "count": 1,
  "has_more": false
}
```

### `GET /sensors` — admin

Query parameters: `bridge_id`, `limit`, `offset`. Ordered by `sensor_id`.

A sensor is registered automatically the first time a bridge posts a reading for
it (first writer wins), so only sensors that have reported at least once are
listed. `last_measurement_at` and `measurement_count` are derived from the
stored readings.

| Field | Type | Notes |
|-------|------|-------|
| `sensor_id` | string | Measuring-station identifier. |
| `bridge_id` | string | Bridge that reported it. |
| `created_at` | string | When the sensor was first seen. |
| `last_measurement_at` | string \| null | Database time of the most recent reading. |
| `measurement_count` | integer | Number of stored readings. |

```bash
curl -s "http://localhost:8000/api/v1/sensors?bridge_id=mostek1" \
  -H "X-API-Key: <admin key>"
```

## Cleaning commands

A command asks a bridge to clean one sensor. The API generates the on-air
payload, so the bridge only has to forward it.

| Field | Type | Notes |
|-------|------|-------|
| `id` | integer | Primary key. |
| `bridge_id` | string | Target bridge. |
| `sensor_id` | string \| null | Target sensor. |
| `command_type` | string | Currently always `clean`. |
| `payload` | string | LoRa string, e.g. `sensor1;clean;`. |
| `status` | string | `PENDING`, `ACKNOWLEDGED` or `REJECTED`. |
| `created_at` | string | ISO 8601 UTC, database clock. |
| `responded_at` | string \| null | When the bridge answered. |
| `response_note` | string \| null | Reason supplied on rejection. |

### Lifecycle

```
            POST /commands (admin)
                     │
                     ▼
                 ┌─────────┐   POST /commands/{id}/ack     ┌──────────────┐
                 │ PENDING │ ─────────────────────────────▶│ ACKNOWLEDGED │
                 └─────────┘                               └──────────────┘
                     │
                     │  POST /commands/{id}/reject
                     ▼
                 ┌──────────┐
                 │ REJECTED │
                 └──────────┘
```

Answering an already-answered command returns `409`.

### `POST /commands` — admin

Queue a cleaning command for a bridge.

```bash
curl -s -X POST http://localhost:8000/api/v1/commands \
  -H "X-API-Key: <admin key>" \
  -H "Content-Type: application/json" \
  -d '{"bridge_id": "mostek1", "sensor_id": "sensor1", "command_type": "clean"}'
```

```json
{
  "id": 1,
  "bridge_id": "mostek1",
  "sensor_id": "sensor1",
  "command_type": "clean",
  "payload": "sensor1;clean;",
  "status": "PENDING",
  "created_at": "2026-10-18T12:44:50Z",
  "responded_at": null,
  "response_note": null
}
```

An unknown `bridge_id` returns `404`.

### `GET /commands` — bridge or admin

Query parameters: `status` (e.g. `PENDING`), `limit`, `offset`. Admins may also
pass `bridge_id`. A bridge only sees its own commands, newest first.

```bash
# A bridge polls for work:
curl -s "http://localhost:8000/api/v1/commands?status=PENDING" \
  -H "X-API-Key: <bridge key>"
```

### `GET /commands/{id}` — bridge or admin

Returns one command visible to the caller.

### `POST /commands/{id}/ack` — bridge

Confirm the command was read; the bridge is about to send `payload` to the
field network.

```bash
curl -s -X POST http://localhost:8000/api/v1/commands/1/ack \
  -H "X-API-Key: <bridge key>"
```

The response is the command with `status: "ACKNOWLEDGED"` and a `responded_at`.

### `POST /commands/{id}/reject` — bridge

Negate the command, optionally recording why.

```bash
curl -s -X POST http://localhost:8000/api/v1/commands/1/reject \
  -H "X-API-Key: <bridge key>" \
  -H "Content-Type: application/json" \
  -d '{"note": "sensor offline"}'
```

The body is optional; `note` is limited to 255 characters.

## Bridge integration sketch

A bridge only needs two loops:

```text
# every reading
POST /api/v1/measurements          {sensor_id, value_mm, sent_at}

# every poll interval
GET  /api/v1/commands?status=PENDING
for each command:
    send command.payload over LoRa           # e.g. "sensor1;clean;"
    POST /api/v1/commands/{id}/ack           # or .../reject {"note": "..."}
```
